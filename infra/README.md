## Выданный сервер — важное

`master@89.126.192.65`, Ubuntu 22.04, 2 CPU / 7,8 ГБ / 97 ГБ. **Это не пустая машина:**
на ней работает боевой S-Munai — `smunai-site.service` (Nitro SSR, 127.0.0.1:3000),
`smunai-leads.service` (CRM, 127.0.0.1:4000) и **системный Caddy, занимающий 80 и 443**
(домены s-munai.kz, crm.s-munai.kz и блок `:80` для доступа по IP).

Из этого следуют два правила:

1. **Не занимать 80/443 своим контейнером.** `docker-compose.yml` из этого каталога поднимает
   собственный Caddy на 80/443 — на этом хосте он не стартует, а попытка «освободить порты»
   уронит боевой сайт и CRM. Использовать `docker-compose.hosted.yml`: он публикует
   backend на `127.0.0.1:8100`, frontend на `127.0.0.1:3100` и наружу ничего не открывает.
2. **Внешний адрес даёт существующий Caddy** — одним добавленным site-блоком из
   `caddy-site.snippet`. Блок по имени хоста матчится раньше общего `:80`, поэтому
   боевые сайты продолжают работать без изменений. Перед правкой — бэкап конфига,
   после — `caddy validate` и `systemctl reload` (без разрыва соединений).

**Домен и TLS уже готовы (22.09).** `pushin.codes` куплен, A-запись → 89.126.192.65,
site-блок добавлен в системный Caddyfile, сертификат Let's Encrypt выпущен (до 21.12.2026).
Проверка живости, не зависящая от контейнеров: `https://pushin.codes/_up` → `caddy ok`.
Пока контейнеров нет, корень отдаёт честную 503 с текстом. HTTP редиректит на HTTPS.

`www.pushin.codes` **в сертификат не входит** — эта запись всё ещё смотрит на парковку
Namecheap. Если нужен www, сначала поправить DNS, потом добавить имя в site-блок.

Бэкап конфига перед правкой: `/etc/caddy/Caddyfile.bak.2026-09-22-132018`.
Откат: `sudo cp /etc/caddy/Caddyfile.bak.2026-09-22-132018 /etc/caddy/Caddyfile && sudo systemctl reload caddy`.

## Деплой без GitHub

`server-setup.sh` делает bare-репозиторий `/srv/hackalem.git` с хуком: любой `git push deploy main`
выкладывает код в `/srv/hackalem` и запускает `infra/deploy.sh`. Это снимает зависимость от
доступа сервера к приватному репозиторию организатора и от того, доживёт ли GitHub до площадки.

```bash
git remote add deploy hackdeploy:/srv/hackalem.git   # алиас уже в ~/.ssh/config мастера
git push deploy main
```

**Проверено 22.09.** Один нюанс, на который напоролись: `server-setup.sh` запускается под
`sudo`, поэтому `git init --bare` создавал `objects/` и `refs/` от root внутри каталога,
принадлежащего пользователю, и каждый push падал с `unable to create temporary object
directory`. В скрипте `chown` теперь идёт **после** `git init`.

Запасной путь — обычный `git pull` на сервере: тогда нужен доступ к приватному репозиторию
(классический PAT в credential store; deploy key недоступен — прав администратора у нас нет).

## Требования к сервисам (для Кубы и Сулы)

- `backend/Dockerfile`, слушает `0.0.0.0:8000`, отдаёт `GET /health` → `{"ok": true}`. Читает `OPENAI_API_KEY` из окружения.
- `frontend/Dockerfile`, слушает `0.0.0.0:3000`, статика или dev-сервер — неважно. API зовёт по относительному пути `/api/...` — Caddy проксирует.
- SSE идёт через `/api/runs/{id}/events` — в блоке Caddy уже `flush_interval -1`.
- **Фиксировать версии** базовых образов и зависимостей: жюри запускает в чистом окружении через несколько дней.

## Если сервер недоступен с Wi-Fi площадки

Телефон как точка доступа → ssh через него. Заранее знать, чей телефон и что у него хватает трафика.
Если сервер недоступен совсем — не паниковать: прод не обязателен (п. 8.7), обязателен
работающий клон. Записать в README, что развёрнутая версия временно недоступна.
