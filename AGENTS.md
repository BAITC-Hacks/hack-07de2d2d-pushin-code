# HackAlem AI — фундамент. Неизменен. Остальное — на усмотрение исполнителя

Один файл для Claude Code и Codex (`CLAUDE.md` → симлинк сюда). Стек, библиотеки, MCP, скилы — каждый свои; ограничений на реализацию нет. Есть семь правил.

1. **Контракт — закон.** `docs/CONTRACT.md`: сущности, API, экраны, один сквозной сценарий. Меняет только мастер; версия в шапке. Перед каждой задачей перечитай — версия могла смениться.
2. **Чекпоинт каждые 30 минут:** `scripts/checkpoint.sh "[T3] что сделано"`. Номер задачи из `BOARD.md` обязателен — по нему мастер сверяет пуш с планом. Без подтверждённого результата за любой отчётный час — дисквалификация (положение, п. 6.6).
3. **Проект должен подниматься из чистого клона — это условие допуска.** `git clone` → `cp .env.example .env` → `docker compose up` → сценарий проходит. П. 5.4.16: «если итоговую версию не удаётся запустить по инструкциям в Репозитории, Команда не допускается к дальнейшему отбору. Дополнительные пояснения и исправления не принимаются». Плюс п. 5.6.6: проверка **без личных аккаунтов** — поэтому живой `https://pushin.codes` с нашим ключом обязателен как демо-доступ.
4. **Агент делает, а не отвечает — и без имитации.** Инструменты, которые модель выбирает сама; последний — действие (`create_*`, `block_*`, `assign_*`); след решения виден на экране по схеме `docs/references/trace-event-schema.md`. **Мок на главном пути запрещён.** Критерии оценки теперь задаёт ТЗ задачи (п. 5.5) — читай `docs/RUBRIC.md`, мастер пишет его по ТЗ в 13:00. Нужна заглушка — помечай её в README.
5. **Только этот репозиторий, только на площадке** (п. 5.4.9, 5.1.7). Заготовки раскрыты в README (п. 5.4.4). **Итоговая версия — содержимое репозитория в 18:00** (п. 5.4.13): последний push в **17:40**, «докоммитим потом» не существует. Секреты — в `.env`; ключ OpenAI — из окружения, никогда в коде. **Никакого чужого или рабочего кода** (в т.ч. S-Munai): организатор получает право использовать, менять и передавать третьим лицам всё, что в проекте (п. 6.1.2–6.1.4).
6. **Счёт — главная мерка.** `docs/SCORE.md` считает мастер по `docs/RUBRIC.md` (v3 — по ТЗ задачи трека «Энергетика», пишется в 13:00). Цель — 100/100. Задачи в `BOARD.md` выводятся из разрывов счёта. Берёшь незанятую сверху, пишешь `@имя`. Появилась идея — строка в «Идеи», не код.
7. **Идентификаторы, коммиты, имена файлов — английский.** Тексты для жюри (README, интерфейс) — русский.

**Роли.** Абылай — мастер: контракт, доска, счёт, слияние, деплой, README, сдача; продуктовый код не пишет. Куба — backend по умолчанию. Сула — frontend по умолчанию. Умолчание переопределяется заявкой в доске.

**Документы.** `docs/hackathon/criteria.md` · `playbook.md` · `cases-forecast.md` · `regulation.md`. `docs/references/` — готовые куски по желанию; обязательна только схема событий.

## Локальная доставка задач

`RTK.md` — каноническое руководство по приёму plain-language задач, изолированным worktree,
проверкам, коммитам и review-доставке. Этот workflow не использует Jira или другую внешнюю
систему планирования: текст задачи — единственный intake.

Используй skill `worktree-delivery` для каждой задачи и роли `task-worker` и
`delivery-reviewer`. Все операции Git/worktree, проверки, push и pull/merge-request выполняются
через `bash scripts/taskflow/tf.sh` после того, как `doctor` подтвердит самостоятельный checkout
с `origin`:

```text
bash scripts/taskflow/tf.sh doctor
bash scripts/taskflow/tf.sh start
bash scripts/taskflow/tf.sh list
bash scripts/taskflow/tf.sh commit
bash scripts/taskflow/tf.sh verify
bash scripts/taskflow/tf.sh ship
```

`ship` отправляет ветку в `origin`, создаёт или обновляет ровно один GitHub pull request либо
GitLab merge request, добавляет в тело задачи точные результаты всех проверок и пытается открыть
URL в браузере. Слияние, approve и deploy запрещены; если браузер не открылся, URL всё равно
выводится пользователю.
