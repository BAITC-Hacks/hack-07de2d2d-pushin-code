# Контракт · **v1** · 23.09 13:45 · заморожен · меняет только мастер

**Продукт:** агент диспетчера ВЭС. На каждую дату выпуска сам берёт архивный прогноз погоды,
доступный на момент выпуска, считает почасовую выработку на 48 ч с интервалом P10–P90,
анализирует результат, пересчитывает при обновлении погоды и публикует выпуск.
Задача — `docs/hackathon/task.md`. Данные — `docs/DATA_NOTES.md`.

## 1. Время и выпуски
- Внутри — только **UTC**. В файлах и на экране — местное **UTC+5** (Asia/Almaty после 01.03.2024).
- Выпуск `D` (issue_date) = момент **T = (D+1) 00:00 местного** (= D 19:00 UTC). На T известна SCADA до D 23:50.
- Горизонт `h = 1…48`: целевые часы (D+1) 00:00 … (D+2) 23:00 местного.
- **Тест:** D = 2026-01-31 … 2026-02-27 — 28 выпусков, покрывают 01.02–28.02.
- **Бэктест для метрики:** D = 2025-12-31 … 2026-01-29 (факт известен).

## 2. Правило «без будущего» — главная проверка задачи
- Погода — Open-Meteo Previous Runs API: для `h = 1…24` → `*_previous_day1`, для `h = 25…48` →
  `*_previous_day2`. Так прогон всегда инициализирован **не позже T**. `previous_day0`, факт и реанализ
  в признаках прогноза **запрещены**.
- У каждой строки прогноза хранится `weather_init_max_utc` — верхняя граница времени прогона. `verify.py`
  проверяет `weather_init_max_utc ≤ T` для всех строк.
- SCADA-признаки (если есть) — только до T.
- **Обучение — на тех же лагах:** признаки `previous_day1/day2` против фактической мощности
  (данные с ~06.2024). Модель сама учит ошибку погодной модели.

## 3. Данные и хранение
| Путь | Что | В git |
|---|---|---|
| `data/raw/turbine_{1,2}.csv` | как выдано | да |
| `data/processed/hourly.parquet` | `ts_utc, turbine, wind_ms, power, temp_c, valid` | нет (генерится) |

| `outputs/forecasts/{D}.csv` | выпуски | да, к сдаче |

- `valid = false`: пропуски, простой (мощность < 0.02 при ветре > 5 м/с), 18.05–17.07.2024 у турбины 1.
- `SCADA_UTC_OFFSET_H` в конфиге, 5 или 6 — выбирается по бэктесту.
- **ВЭС (`plant`) = среднее нормированной мощности двух турбин.**

## 4. Модель
- Признаки: ветер 100 м (и 10 м, если есть), ветер³, направление sin/cos, температура, час, месяц, `h`, турбина.
- Цель: часовая нормированная мощность. Выход **P10/P50/P90**, обрезка в [0, 1], P10 ≤ P50 ≤ P90.
- Для бэктеста января учим на данных < 2026-01-01, для февраля — на всём до 31.01.2026.
- Базовые линии (обязательны, для метрики): персистентность (последние 24 ч), климатология час×месяц,
  кривая мощности от прогнозного ветра.
- Метрики: **nMAE, nRMSE** (мощность уже нормирована = % от номинала), по горизонту и по дням.

## 5. Агент
Инструменты — детерминированные функции. Порядок и решения — за LLM (OpenAI, function calling).
Числа прогноза **считает только модель**, LLM их не придумывает и не правит.

| Инструмент | Вход → выход |
|---|---|
| `fetch_weather(issue_date, run="latest"\|"previous")` | погода на окно, с `init`-метками, из кэша или API |
| `check_data(issue_date)` | пропуски, свежесть прогона, доступность источников |
| `run_model(issue_date, weather)` | P10/P50/P90 по часам × {1, 2, plant} |
| `analyze_forecast(run_id)` | JSON-сводка: ветер > 20 м/с, обледенение (t ∈ [−3; +1] °C), расхождение погодных моделей, рампы > 0.4/ч, скачок против прошлого выпуска |
| `recalc_forecast(issue_date, reason)` | повтор с обновлённой погодой → новая версия |
| `publish_forecast(issue_date, version, summary)` | **действие**: пишет CSV и запись в журнал выпусков |

- **Повторный расчёт.** v1 — на более старом прогоне (`previous_day2` на всё окно). Событие «вышел новый
  прогон» (`previous_day1` для h ≤ 24) будит агента: если средний сдвиг ветра > 0.5 м/с или флаг анализа —
  пересчёт → v2 с объяснением «почему изменилось».
- **Без `OPENAI_API_KEY`** — детерминированный режим: тот же порядок, анализ по шаблону, **те же числа**.
- Лимит 8 шагов. След — строго по `docs/references/trace-event-schema.md`; `publish_forecast` → `type: action`.

## 6. API (backend, FastAPI, порт 8000)
- `GET /health` → `{"ok": true}`
- `GET /api/issues` → `[{"issue_date","status","version","published_at"}]`
- `POST /api/runs` `{"issue_date":"2026-01-31","mode":"agent"|"deterministic"}` → `{"id"}`
- `GET /api/runs/{id}/events` — SSE, `data: <event>`
- `GET /api/runs/{id}` → `{"done","artifact":{"issue_date","version","csv_url"},"events":[...]}`
- `POST /api/backtest` `{"from":"2026-01-31","to":"2026-02-27"}` → `{"id"}` (выпуски подряд, события по каждому)
- `GET /api/forecasts/{issue_date}` → `{"issue_date","version","summary","rows":[{"target_time_local","h","turbine","p10","p50","p90","actual","flags"}]}` (`actual` = null, если факта нет)
- `GET /api/forecasts/{issue_date}.csv`
- `GET /api/metrics` → бэктест января: модель и базовые линии, nMAE/nRMSE, по горизонту
- Ошибки: 400 с текстом для неверной даты / даты вне диапазона, 404 для неизвестного id. Не 500.

## 7. Формат выпуска (CSV)
`issue_date, issue_time_local, target_time_local, horizon_h, turbine, p10, p50, p90, wind_fc_ms, weather_init_max_utc, version`
`turbine ∈ {1, 2, plant}`. 48 × 3 строк на выпуск. Плюс сводный `outputs/forecast_feb2026.csv`.

## 8. CLI — для эксперта, без UI
```
python -m windcast.backtest --from 2026-01-31 --to 2026-02-27   # 28 выпусков → outputs/forecasts/
python -m windcast.evaluate --from 2025-12-31 --to 2026-01-29   # метрики января
python scripts/verify.py                                        # PASS/FAIL по проверкам
```

## 9. Экраны (frontend, порт 3000, API по `/api/...`)
1. **Прогноз:** выбор даты выпуска, график P50 + полоса P10–P90, факт поверх (январь), турбина 1/2/ВЭС,
   версия v1/v2, текст анализа, «Скачать CSV».
2. **След агента:** панель событий, кнопки «Запустить выпуск» и «Прогнать февраль».
3. **Качество:** метрики января против трёх базовых линий, ошибка по горизонту.

## 10. Сквозной сценарий демо
31.01.2026 → «Запустить выпуск» → след: `fetch_weather` (прогон ≤ T) → `check_data` → `run_model` →
`analyze_forecast`: «модели расходятся на 3 м/с 02.02 14–18 ч» → событие «новый прогон» → `recalc_forecast` →
`publish_forecast` v2 (**action**) → график с полосой → CSV. Затем «Прогнать февраль» → 28 выпусков.
