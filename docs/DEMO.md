## Вопросы жюри и ответы

**1. Зачем LLM, если правила дают те же числа?**
Числа обязаны совпадать: их считает модель, LLM их не придумывает и не правит — это принцип, а не недостаток.
LLM решает то, что правилом не запишешь заранее: порядок шагов, пересчитывать ли после нового прогона и почему,
повторить ли запрос при сбое источника или продолжить с предупреждением, и пишет сводку диспетчеру простым
языком со строкой «что изменилось». Все 29 февральских решений о пересчёте принял LLM (`meta.by = "llm"` в
каждой ленте). Код держит рамки: сводку с числами не из ответов инструментов не публикует (так было 08.02 и
25.02 — взял шаблонную), пересчёт на позднем прогоне не разрешает. Детерминированный режим — гарантия
проверяемости без ключа и запасной путь, если LLM недоступна.

**2. Где защита от утечки будущего?**
Три слоя. В коде: `timeline.py` считает `init + 8 ч ≤ T`; `fetch_weather` и `check_data` не пропускают
прогон, вышедший после T; `recalc_forecast` отказывает в пересчёте на нём; `predict` отказывает, если граница
обучения артефакта позже момента выпуска. LLM выбирает только `run = "previous" | "latest"`, время старта
вычисляет код. В признаках нет факта, реанализа, SCADA и `previous_day0`; модель для февраля обучена на данных
до 31.01.2026 19:00 UTC. В записи: у каждой строки CSV `weather_init_max_utc`, у каждого прогона в `{D}.json` —
`before_issue`. В независимой проверке: `scripts/verify.py` не импортирует код продукта, правила времени
записаны в нём заново; 4176/4176 строк и 174/174 прогонов — PASS.

**3. Почему не ECMWF напрямую?**
Нужен архив прошлых прогонов на каждый час для каждой даты с 06.2024 по координатам ВЭС и без ключа — это даёт
Open-Meteo Previous Runs API (`previous_day1…4`). `best_match` — модель, которую Open-Meteo подбирает для
точки: ECMWF IFS, DWD ICON, NOAA GFS. Задержку публикации взяли по ECMWF (7–8 часов) как самую консервативную.
Одна погодная модель — наше известное ограничение; ансамбль ECMWF IFS + GFS + ICON, которые тоже есть в
Previous Runs, — первый шаг развития.

**4. Насколько точно?**
Январь 2026, ВЭС, 30 выпусков, 1417 часов с фактом: nMAE 15,8 % номинала против 19,4 % у кривой мощности,
26,8 % у климатологии, 36,5 % у персистентности — на 18,5 % лучше лучшей базовой линии, в 2,3 раза лучше
персистентности. По nRMSE выигрыш над кривой мощности небольшой: 23,45 против 23,99 — крупные промахи идут
от ошибки прогноза ветра. Первые сутки 14,6 %, вторые 17,0 %. Покрытие P10–P90 — 80,5 % при цели ≈ 80 %,
смещение P50 −1,5 п.п. Без прогноза погоды лучшие модели на истории SCADA ошибаются в 1,7–1,9 раза сильнее
(MAE 0,27–0,30 против 0,158).

**5. Почему именно 8 часов?**
Глобальные модели стартуют в 00, 06, 12 и 18 UTC; ECMWF публикует открытые данные примерно через 7–8 часов,
остальные быстрее. Архив не хранит реальный момент выхода каждого прогона, поэтому взяли 8 часов как
константу, консервативную для любой модели. Следствие: самый свежий допустимый прогон — D 06:00 UTC, часы
18–48 берут прогон на 6–24 часа старше. Без задержки прогон D 18:00 UTC формально «до T», но опубликован после
него — это утечка. Цена честности измерена: 15,0 % → 15,8 % nMAE, 0,8 п.п.

**6. А факт за февраль?**
Данных за февраль организатор не дал: SCADA кончается 31.01.2026 23:50. Точность февраля мы не считаем и не
придумываем. Качество показано на январе тем же путём и по тому же правилу. Февральские выпуски — 29 CSV по
144 строки плюс сводный `outputs/forecast_feb2026.csv` (4176 строк) с P10/P50/P90 по турбинам и ВЭС — готовы
для сверки организатором; в каждой строке есть `weather_init_max_utc`.

**7. Что работает без ключа?**
Всё. `docker compose up --build` без `.env` → `"mode": "deterministic"`: тот же цикл по правилам
(`meta.by = "rule"`), та же политика пересчёта, те же P10/P50/P90 — на 29 выпусках все v1 и v2 совпали строка
в строку, отличаются только тексты сводок. Без сети погода берётся из `data/weather_cache/` (60 файлов),
январь и февраль воспроизводятся офлайн. На https://pushin.codes стоит ключ команды, режим LLM, регистрация не
нужна (п. 5.6.6).

**8. Как воспроизвести?**
`git clone https://github.com/BAITC-Hacks/hack-07de2d2d-pushin-code` → `docker compose up --build` →
http://localhost:8080; `curl http://localhost:8080/health` → `issues_ready: 29`, все `ports` — `real`;
`python3 scripts/verify.py` → PASS, 14 проверок. Перевыпустить февраль с нуля:
`PYTHONPATH=backend python -m windcast.backtest --from 2026-01-31 --to 2026-02-28 --mode deterministic`
(≈ 35 с; с ключом и `--mode agent` ≈ 6 мин). Метрики января: `python -m windcast.evaluate --from 2025-12-31
--to 2026-01-29` (≈ 1,5 мин) — воспроизводит `outputs/metrics_jan.json` байт в байт. Чистый клон без `.env`
проверен 23.09 в 16:17 (README § 6.5).
